## Source map

Product namespace, not colliding historical REPO-D IDs: D-053 (stable internal identity, bounded sessions, rotating refresh with reuse detection, independent previously verified email before history after risk, record and notify number recovery, delivery facts alone prove nothing); D-052 (separate staff identity with mandatory TOTP, no SMS second factor — distinct from customer phone OTP); D-057 (typed, bounded, versioned settings; ownership/ledger/food/payment invariants cannot be configured away); D-059 (PostgreSQL/Supabase, TypeScript modular backend and a separate durable worker, shared versioned contracts, no client database secrets). Security requirements SEC-01 (normalize phone, enforce uniqueness, expire and atomically consume purpose-bound OTP challenges, never log OTPs), SEC-02 (shared quotas by number/IP/context, resend cooldown, bounded attempts, spend limits, non-enumerating responses) and SEC-04 (independent prior proof for risky recovery/number changes, reauthentication, audit and notification). Functional requirements FR-001 (stable internal identity; phone is the sign-in identifier; current number control alone does not prove history ownership), FR-002 (no customer password), FR-003 (one normalized phone maps uniquely; number recycling never silently transfers history), FR-004 (OTP verifies current number control, not each request; silent rotating refresh within bounded limits), FR-005 (avoid unnecessary SMS; a new device, missing/expired session or changed number may require OTP; risky access also requires independent proof), FR-006 (no email required at claim; verified at the payment summary), FR-007 (verified email as independent recovery proof, unique per account, never an email/password sign-in), FR-038 (short access tokens, rotating refresh with reuse detection, finite idle/absolute lifetime), FR-039 (revocation takes effect on the next request), FR-040 (owner sees and revokes device sessions; single and bulk revoke share the same independent proof), FR-041 (recoverable via OTP plus independent proof; audited assisted procedure when proof is unavailable) and FR-044 (record phone history so identity continuity survives number changes). Research R1 (Supabase Auth phone OTP and stable `customer_accounts.id`), R2 (no `getUser()`-alone liveness; enforce session status, ownership, risk and bounded lifetime; fail closed on unavailable validation), R3 (`auth.admin.signOut` takes a JWT, not a session UUID; app-level revocation record; server-only owner-scoped listing) and R4 (local-only test OTPs; live supplier credentials stay server-side and require qualification).

## Invariants under review

- OTP (SEC-01/SEC-02): purpose-bound expiring single-use challenges; shared multi-instance quota by number/IP/context checked before send; idempotency; ambiguous-send reconciliation that consumes the reservation and forbids blind retry; bounded verification attempts; non-enumerating responses; no victim lockout. `providerQualified=false`.
- Risk (SEC-04/D-053/FR-001/038): stable internal identity; phone OTP alone never unlocks history; independent previously verified email proof, account/action bound and single-use; single and bulk revoke share the same proof; unavailable validation denies.
- Recovery (SEC-04/D-053/FR-041/044): delivery facts and newly added email prove nothing; a factor is never replaced using only that factor; both factors lost resolve to audited assistance without automatic unlock; missing independent evidence denies history and identity transfer; support approval alone is never sufficient. Completed assisted recovery and number replacement both carry a mandatory SEC-04 security notification.

## Trust boundary

Model helper inputs are authoritative synthetic server records, never browser assertions. A browser-supplied value has no authority; any value that is not a strict, well-formed server fact fails closed. The runtime application must load actual principal/account/action/session/risk/factor/event/channel records, check resource ownership, atomically consume the one-use proof, and maintain an audited transactional outbox with authenticated, deduplicated callbacks, bounded retries and failure alerts.

## Review scope and limits

The reference model is a decision fixture, not a shared ledger, not a provider integration and not a proof of distributed atomicity. `verification.distributedAtomicityProven=false`, `providerBehaviorProven=false` and `noProductionWritesAttested=false`; independent qualified review remains required and full acceptance is not claimed. The reference tests run only in an isolated author container and touch no production, database or live provider. `providerQualified=false` refers to the live OTP provider, not to any LLM provider; separate operator LLM funding does not change the authority flags.
