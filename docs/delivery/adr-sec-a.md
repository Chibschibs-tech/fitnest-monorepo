# ADR: OTP abuse, risk and recovery design (S001-SEC-A)

Status: Proposal (unratified). Task key: S001-SEC-A. Source baseline: `2854038dfe653289c326dd33650a311918f630ad`. Authority: no production writes authorized, no gates approved, no budget approved, no task accepted.

## Context

001 (`specs/001-identity-account-admission/spec.md`) gives customers a phone-OTP identity with a stable internal account, bounded sessions and independent verified-email recovery proof. The product baseline (`docs/delivery/product-baseline.md`) and the clarification register (`docs/delivery/clarifications.md`) settle the invariants this design must respect while leaving five decisions open under G-SESSION, G-RECOVERY, G-PROVIDERS and G-BUDGET. This ADR records the abuse, risk and recovery design as an isolated reference model, separates what is settled from what remains unratified, and asserts no production writes.

Source map (product namespace, not colliding historical REPO-D IDs): D-053 (stable internal identity, bounded sessions, rotating refresh, independent previously verified email before history after risk, record and notify number recovery, delivery facts alone prove nothing); D-052 (separate staff identity with mandatory TOTP, no SMS second factor — distinct from customer phone OTP); D-057 (typed, bounded, versioned settings; ownership/ledger/food/payment invariants cannot be configured away); D-059 (PostgreSQL/Supabase, TypeScript modular backend and a separate durable worker, shared versioned contracts, no client database secrets — the substrate for a transactional outbox). Security requirements SEC-01 (phone normalization, uniqueness, expire and atomically consume purpose-bound OTP challenges, never log OTPs), SEC-02 (shared quotas by number/IP/context, resend cooldown, bounded attempts, spend limits, non-enumerating responses) and SEC-04 (independent prior proof for risky recovery/number changes, reauthentication, audit and notification). Functional requirements FR-001 (stable internal identity; phone is the sign-in identifier; current number control alone does not prove historical-data ownership), FR-002 (no customer password), FR-003 (one normalized phone maps uniquely; number recycling never silently transfers history), FR-004 (OTP verifies current number control, not each request; silent rotating refresh within bounded limits), FR-005 (avoid unnecessary SMS; a new device, missing/expired session or changed number may require OTP; risky access also requires independent proof), FR-006 (no email required at claim; verified at the payment summary), FR-007 (verified email as independent recovery proof, unique per account, never an email/password sign-in), FR-038 (short access tokens, rotating refresh with reuse detection, finite idle/absolute lifetime), FR-039 (revocation takes effect on the next request), FR-040 (owner sees and revokes device sessions; single and bulk revoke share the same independent proof), FR-041 (recoverable via OTP plus independent proof; audited assisted procedure when proof is unavailable) and FR-044 (record phone history so identity continuity survives number changes). Research R1 (Supabase Auth phone OTP and stable `customer_accounts.id`), R2 (no `getUser()`-alone liveness; enforce session status, ownership, risk and bounded lifetime; fail closed), R3 (`auth.admin.signOut` takes a JWT, not a session UUID; app-level revocation record; server-only owner-scoped listing), R4 (local-only test OTPs; live supplier credentials stay server-side and require qualification).

## Decision

Adopt the following fixed invariants as the design contract. They are recorded verbatim in `docs/delivery/contracts/S001-SEC-A.json` and encoded as a frozen reference model in `tests/security/identity-reference.mjs`. The model is illustrative where the gate is still open, never a deployed default.

### Trust boundary

The reference model's helper inputs are authoritative synthetic server records, never browser assertions. `classifySendResult` consumes a provider dispatch record; `canReserveBeforeSend` consumes a ledger record; `sessionValid` consumes a server session record; `canUnlockHistory` consumes principal/account/action/session/risk/factor records; `securityNotificationIntent` consumes account/source-event/channel records. A browser-supplied value has no authority in these fixtures: any value that is not a strict, well-formed server fact fails closed. This is the same boundary the runtime application must enforce with real records.

## Challenge Expiry and Single-Use

Per SEC-01, OTP challenges are purpose-bound, expiring and atomically consumed. A challenge is bound to a normalized phone, a purpose (sign-in, recovery, number change) and an idempotency key; it expires after a short window and is validated at most once. Concurrent validation against the same challenge must result in exactly one successful consumption (SEC-01's minimum evidence), so expired or replayed codes fail and no duplicate account appears. OTP values are never logged. In the reference model, `classifySendResult` + `shouldConsumeReservation` model the send half of this contract: a sent or ambiguous outcome consumes the reservation, and the challenge remains single-use. The runtime must additionally bind the challenge to its purpose key, compare it under constant time and mark it consumed in the same transaction that records the outcome (see "Runtime application obligations").

## Multi-Instance Quota

Per SEC-02, OTP quotas are shared across instances by number, IP and context, with a resend cooldown, bounded spend and non-enumerating responses. `quotaBeforeSend` plus `sharedAtomicAccountingRequired` mean a reservation is taken before any send and is enforced on shared storage so that distributing calls across instances cannot evade the quota. R4 flags cross-instance spend/quota protection as still unqualified: the reference model (`canReserveBeforeSend`) is a decision fixture for that logic, not the shared ledger itself. A positive safe-integer `units` and a nonnegative safe-integer `quotaRemaining` are required; a fresh insufficient quota denies without consuming, a fresh sufficient quota reserves. No victim lockout: quota exhaustion never permanently blocks an account — it only delays new sends under cooldown, so abuse cannot lock a legitimate victim out (SEC-02).

## OTP Ambiguity and Idempotency

Per SEC-02 and FR-011's capacity-response flow, sends are idempotent and ambiguous outcomes are reconciled without duplicate delivery. `idempotencyRequired` binds each send to its purpose key so a retried request reuses the existing reservation. `ambiguousSendConsumesReservation` with `blindRetryAllowed=false` means an unknown provider outcome consumes the reservation and is never blindly retried, because retrying on unknown could deliver a duplicate OTP — the exact abuse the task targets. A replayed reservation returns its old state and never permits another send; unknown outcomes retain quota and cannot blindly retry. In the reference model, `classifySendResult` returns `ambiguous` for missing/malformed results, a missing strict `delivered` boolean, an invalid `outcomeUnknown`, or `outcomeUnknown === true` even when `delivered === true` is also asserted; `shouldConsumeReservation(sent|ambiguous)` is true, and `allowRetry` is true only for an explicit `not_sent` and means eligibility for further checks, not a send authorization. No mock proves distributed atomicity or provider delivery.

## Verification Attempt Bounds

Per SEC-02, OTP verification attempts are bounded. The reference model's `verifyAttemptAllowed` accepts only safe-integer counters from zero through `maxVerificationAttempts - 1`; malformed, negative and fractional counters deny. The value `5` is illustrative and unratified, never a deployed default. Bounded attempts plus a resend cooldown and non-enumeration together mean brute force cannot exhaust a legitimate account's path to recovery and cannot distinguish existing from non-existing accounts.

## Non-Enumerating Responses

Per SEC-02, account existence is never revealed. `accountLookupResponse` always returns `generic` regardless of whether the account exists, so an attacker cannot distinguish "no such number" from "wrong code" or "cooldown active". This applies to both the send and the verification responses, including the ambiguous-send path: a sender learns nothing about account existence from a generic outcome.

## Bounded Sessions

Per FR-038, D-053 and R2, sessions have short access tokens, rotating refresh with reuse detection, and finite idle and absolute lifetime. The reference model's `sessionValid` requires a finite nonnegative server time and finite nonnegative `accessExpiresAt`/`absoluteExpiresAt`/`lastActivityAt` facts, denies a future `lastActivityAt`, requires `now` strictly before both expiries, and requires the idle gap strictly below the illustrative idle limit. The reference limits — access 600s, idle 30 days, absolute 90 days — are illustrative and unratified, never deployed defaults (G-SESSION). R2 rejects `getUser()`-alone liveness: after validating token/principal, the runtime must enforce session status, ownership, risk clearance and bounded lifetime at the authorization boundary, and fail closed when validation is unavailable. FR-039's revocation takes effect on the next request across every exposed data path; FR-004/FR-005 keep ordinary same-device returns SMS-free within these bounds.

## Prior Proof for Risk

Per SEC-04, FR-001, FR-038 and D-053, a stable internal identity never allows phone-OTP control alone to unlock historical data after a risk signal. Current number control proves current reachability, not ownership of past admission, wallet, referral or history records. The reference model's `canUnlockHistory` requires a known risk signal, a live session validation, nonempty actual account/action, finite nonnegative `now`/`riskObservedAt` with `riskObservedAt <= now`, and an independent server proof whose factor is `verified_email`, previously verified, account-and-action bound, unused, matching the actual account and action, verified before the risk was observed and not expired. Wrong, missing, new, expired, used or unverified proof denies; phone-OTP-only, unknown risk and unavailable validation deny. `validationAvailable` returns true only for live, and `validationDeniesWhenUnavailable` denies on missing/null/unknown/pending/failed/unavailable input, allowing only live — and is never sufficient authorization by itself.

## Recovery Audit and Notification

Per SEC-04 and FR-041, losing a phone is recoverable through OTP plus the independent proof required by D-053; when proof is unavailable the audited assisted procedure applies, with no promise of universal OTP-only or support-free recovery. Delivery facts, address, plan and last delivery are never sufficient evidence (D-053; spec "Recovery and ownership"). A factor is never replaced using only that same factor (`factorReplacementAllowed` admits only differing known factors `phone` and `verified_email`); single and bulk device disconnect share the same independent-proof requirement. `recoveryDecision` requires a literal boolean `bothFactorsLost`: missing or malformed input denies history and identity transfer; both lost with sufficient independent server evidence resolves to audited assistance without automatic unlock, otherwise it denies; both lost false may select factor-based recovery as a route only, without granting historical access. `supportApprovalSufficient` is true only for an independently checked server evidence record, never a support-only assertion or truthy text. Completed assisted recovery and number replacement both require the mandatory SEC-04 security notification (see below), and every recovery action is audit-recorded and notified to the account holder.

## Number Change Notification

Per SEC-04, FR-044 and D-053, phone history is recorded so identity continuity survives number changes, and number recovery is both recorded and notified. Number replacement requires independent prior proof plus verification of the new number (never the same factor alone), and the completed change triggers a security notification to a previously verified trusted channel. The reference model's `securityNotificationIntent` accepts only a synthetic server record with safe nonempty account/sourceEvent/trustedChannel IDs (letters, digits, underscore, hyphen, 1–80 chars), an operation of `recovery_completed` or `phone_replaced`, same-account source event and channel, a previously verified channel, a recorded audit entry, and a channel established strictly before the risk was observed. Invalid, untrusted, newly added, wrong-account or malformed input returns null. The emitted payload is exactly `{ kind: "account_security_change" }` — no telephone, email, OTP, session token or history. Replays keep the same event/recipient/channel key; a different channel changes the key; a supplier outage does not erase the pending intent and grants no historical access.

## Unresolved Choices

These choices are recorded, not decided. They are held in `docs/delivery/contracts/S001-SEC-A.json` with status `unratified`, each with its gate and the actual future ratification/evidence owner:

1. session_durations (G-SESSION; owner Security + product): exact access/idle/absolute limits and refresh-rotation behavior.
2. device_concurrency (G-SESSION; owner Security + product): reconciling 001's multiple revocable devices against 004's single active session and any device-count limit.
3. risk_signals (G-SESSION; owner Security + product): precise taxonomy and thresholds of risk signals.
4. assisted_recovery_evidence (G-RECOVERY; owner Security + support): the evidence checklist and audit fields for assisted recovery.
5. live_provider_and_budget (G-PROVIDERS; owner Operations + engineering, with OTP financial approval under G-BUDGET owned by Founder + orchestrator): supplier selection, secret-manager credentials, templates/consent, failure runbooks and the OTP spend ceiling.

D-053 supersedes unlimited sessions and OTP-only risk fallbacks, but this ADR does not silently approve session times, device counts, risk thresholds, recovery-document policy or suppliers.

## No Production Writes

This proposal authorizes no production writes, no live provider calls, no migrations, no spending, no notification sends and no network access. The authority object in `docs/delivery/contracts/S001-SEC-A.json` is all-false (`productionWritesAuthorized`, `gatesApproved`, `budgetApproved`, `taskAccepted`), and the verification object keeps `referenceModelOnly=true`, `distributedAtomicityProven=false`, `providerBehaviorProven=false`, `noProductionWritesAttested=false`, `independentReviewRequired=true` and `fullAcceptanceClaimed=false`. T013 (production schema apply) and G-RELEASE remain untouched; no gate is approved by this document. The reference tests run only in an isolated author container and touch nothing outside it.

## Runtime application obligations

The reference model is a decision fixture; the runtime application must realize these invariants with real records. On every request it must load actual principal, account, action, session, risk, factor, event and channel records; check resource ownership; atomically consume the one-use proof; and maintain an audited transactional outbox. Concretely, the runtime must (1) commit audit entry + state change + outbox row in one transaction; (2) deliver through authenticated, deduplicated callbacks keyed by event/recipient/channel; (3) retry bounded and alert on repeated failure (SEC-28's transactional outbox pattern). These are future runtime obligations, not demonstrated by this fixture: no mock can prove distributed atomicity, provider delivery or the outbox transaction, and `providerQualified` remains false until a live non-production qualification under G-PROVIDERS and G-BUDGET.

## Rationale

`quotaBeforeSend` with shared atomic reservation directly implements the cross-instance spend protection R4 flags as unqualified, while `idempotencyRequired` prevents duplicate charges on retries. `ambiguousSendConsumesReservation` with `blindRetryAllowed=false` is the only safe stance when the provider cannot report delivery. `phoneOtpAloneUnlocksHistory=false` follows FR-001/FR-038/D-053: current reachability is not ownership of history, and the account/action-bound single-use email proof cannot be replayed to lift the gate twice. `unavailableValidationDenies` follows R2: no positive cache extends access beyond the revocation boundary. Recovery refuses delivery-knowledge and newly-added-email shortcuts because D-053 states delivery facts alone prove nothing.

## Consequences

Nothing here attests execution history; `noProductionWritesAttested` stays false. The design is a reference model only; distributed atomicity and live provider behavior are unproven; independent qualified review is still required. `providerQualified=false` refers to the live OTP provider, not to any LLM provider; separate operator LLM funding does not change the authority flags.

## Reference model

`tests/security/identity-reference.mjs` exports a frozen `CRITERION`, the frozen risk-signal table, illustrative/unratified `SESSION_LIMITS`, and pure functions mirroring these invariants. `tests/security/identity-reference.test.mjs` exercises them with `node:test` (valid paths plus malformed/unknown/expired/replayed/cross-account inputs, notification privacy/deduplication and supplier outage) and asserts the contract shape and fixed values. Run with `node tests/security/identity-reference.test.mjs`. The fixtures are isolated and touch no production, database or live provider.
